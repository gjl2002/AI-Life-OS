## 用户自己的 Notion 接入

本 Skill 使用 `$ai-life-system-init` 定位用户自己的 Notion 结构。执行前先运行 `scripts/runtime.py status`；状态为 `needs_init` 时先引导用户完成初始化。对本次操作涉及的每个概念运行 `scripts/runtime.py resolve --concept <key>`，只使用 Runtime 返回的目标 Data Source ID。读取该 Data Source 的实时 Schema，并在写入前运行 `scripts/runtime.py check-write` 校验本次属性、选项和 relation。

概念映射：`travel, itinerary, location, relationship_circle, expense`。

创建时必须让当前 Notion connector 将新页面的 parent 指向已解析的 Data Source；写入后回读确认 parent 和属性。若概念未找到、结构不兼容、候选不唯一或 connector 无法确认 parent，应停止该写入并说明原因，不得猜 ID、扫描无关空间或复制已有个人记录。以下正文中的数据库路径、字段名、选项和默认值若与用户实时 Schema 不一致，均视为示例而非要求；只有语义和字段类型明确匹配时才映射，否则询问或安全停止。仅读取本次任务所需的数据；不得将用户本地索引、凭据、页面 ID 或个人样例打包发布。

## 场景判断

从用户自然语言判断当前处于旅行的哪个阶段：

| 用户说 | 判断 | 操作 |
|---|---|---|
| "好想去XX"、"想去XX" | **起念（愿望）** | 新建旅行，状态=愿望，只填名称 |
| "X月X号去XX，X号回"、"国庆去XX跟XX" | **定计划** | 新建旅行，状态=计划中，填日期+同行人+类型 |
| "排行程"、"安排每天" | **排行程** | 根据日期逐日创建行程记录 |
| "Day 1 去XX，然后XX" | **排景点** | 在对应行程下创建地点并排第几站 |
| "到XX了"、"去了XX"、"XX打卡" | **出行打卡** | 更新地点状态=已出行，填实际日期 |
| "今天行程结束了"、"Day 1 搞定" | **每日完成** | 勾选当天行程完成？ |
| "旅行结束了"、"回来了" | **旅行复盘** | 旅行状态→已出行，打整体星级 |
| "XX没拍照，帮我加张图" | **补照片** | 搜一张地点照片传到记录上 |
| "Day 3 从成都去重庆"、"中间换城市了" | **多城市移动** | 修改对应天的出发地/目的地 |
| "临时去了一个XX"、"路过XX" | **临时加地点** | 快速新建地点，关联到当天行程 |
| "XX不去了"、"取消这次旅行" | **取消旅行** | 旅行状态→取消/放弃 |
| "改到10月3号"、"和同行人一起出行" | **修改旅行** | 更新旅行属性 |
| "这次旅行花了XX钱" | **旅行支出** | 记账时自动关联到当前旅行 |

## 当前版本：创建旅行

### 输入解析

| 字段 | 来源 |
|---|---|
| 名称 | 目的地名称（如"重庆"、"重庆成都行"） |
| 出发时间 | 用户给具体日期；只说"国庆/五一/周末"时按当年节日推算 |
| 结束时间 | 用户给；只说天数时=出发+天数-1 |
| 同行人 | "跟XX一起"→在人际圈搜；没说→留空 |
| 类型 | 用户说了就选；没说根据语境判断：观光游玩→休闲游；市内逛→城市微旅行；爬山户外→自然户外；演唱会/演出→演出；看亲戚朋友→探亲访友；出差→商务出差 |
| 行程形态 | 根据天数和距离判断：当天来回→当日往返；1-3天周边→周末短途；跨省长距离→长途跨省；出国→出境；长期住→长期居住 |
| 状态 | 只说"想去"没日期→愿望；有日期→计划中 |

**类型选项**（select，不新建）：休闲游、城市微旅行、自然/户外、演出、探亲访友、商务出差、学习考试、其他

**行程形态选项**（select，不新建）：当日往返、周末短途、长途跨省、出境、长期居住

### 执行流程

#### 1. 直接新建记录

在 Runtime 已解析的用户 Data Source 中直接创建新记录；不复制现有记录。


#### 2. 查找同行人（如有）

用 `notion_ai_search`（data_source_url=人际圈）按姓名搜同行人。
- **找到** → 用现有页面 URL
- **没找到** → 不新建，留空（用户后补）

#### 3. 上传旅行照片（目的地风景图）

在 update 旅行属性之前，先找一张目的地好看的风景照：

1. `image_search` 搜 `"<目的地名>" 城市风景 地标 高清`，选一张最能代表这个城市的
2. 追踪直链：`curl -sL -o /dev/null -w "%{url_effective}" "<短链>"`
3. `notion_create_attachment` → 拿 `file_upload_id`
4. 在 update 属性时填入：
   ```json
   "旅行照片": [{"type":"file_upload","file_upload":{"id":"<file_upload_id>"}}]
   ```

> 找不到合适的风景照就留空，告诉用户"照片待补"。

#### 4. 一次性 update 属性

```json
{
  "名称": "<目的地名称>",
  "date:出发时间:start": "YYYY-MM-DD",
  "date:出发时间:is_datetime": 0,
  "date:结束时间:start": "YYYY-MM-DD",
  "date:结束时间:is_datetime": 0,
  "同行/遇见朋友": ["<人际圈页面URL>"],
  "类型": "<类型选项>",
  "行程形态": "<行程形态选项>",
  "状态": "计划中",
  "景点": null,
  "行程": null,
  "支出": null,
  "旅行评价": null,
  "旅行照片": [{"type":"file_upload","file_upload":{"id":"<file_upload_id>"}}]
}
```

新页面只写本次记录明确提供的值；未提供的可选字段留空，不沿用其他记录的属性或正文。
- `景点` → null（一次旅行的景点列表）
- `行程` → null（一次旅行的行程）
- `支出` → null（旧支出关联）
- `旅行评价` → null（旧星级）
- `旅行照片` → 覆盖为新找的目的地风景照（找不到才留空）
- `同行/遇见朋友` → 覆盖为新同行人，没同行人就 null

**愿望模式**（只说想去没日期）：
- 状态 = "愿望"
- 出发时间、结束时间、行程形态 → 都留空（null）
- 只填名称和类型

#### 4. 验证

`notion_fetch` 新记录，确认：
- parent-data-source = 旅行
- 名称、日期、类型落库
- 旧景点/行程/支出已清空

向用户报告填了什么。

## 场景二：排行程（创建每日行程，自动执行）

旅行建好后，**自动**根据出发/结束日期逐日创建行程记录，不需要用户再说"排行程"。

> 创建旅行（有日期）→ 立即接着排行程，一气呵成。

### 触发条件

- 旅行刚创建完，用户说"排行程"、"安排每天"
- 或用户说"给XX旅行排一下行程"

### 输入

| 字段 | 来源 |
|---|---|
| 关联旅行 | 默认找最近一条状态=计划中的旅行；多条则问用户 |
| 出发地 | 用户未说明时留空或询问；仅在用户已确认并持久化偏好时使用 |
| 目的地 | 从旅行名称提取（如"重庆行"→重庆）；多城市旅行从名称提取 |

### 行程命名格式

```
<旅行名称> | <YYYY年MM月DD日> | <出发地> ‣ <目的地> | Day <N>
```

示例：`示例旅行 | 日期 | 出发地 ‣ 目的地 | Day 1`

### 逐日规则

设出发日期 = D1，结束日期 = Dn，总天数 = n。

| 第几天 | 出发地 → 目的地 | 行程日 |
|---|---|---|
| Day 1 | 出发地 → 目的地 | Day 1 |
| Day 2 ~ Day n-1 | 目的地 → 目的地 | Day 2 ~ Day n-1 |
| Day n（最后一天） | 目的地 → 出发地 | Day n |

> 当日往返（n=1）：出发地 → 目的地 → 当天回，只建一条 Day 1，出发地=目的地=出发地（往返）。

### 执行流程

#### 1. 确定旅行和天数

从旅行记录取 `date:出发时间:start` 和 `date:结束时间:start`，计算总天数。
若旅行还没设日期 → 先问用户日期。

#### 2. 逐日新建行程记录

对每一天 Day 1 ~ Day n：

1. 在 Runtime 已解析的用户 Data Source 中直接创建新记录，不以其他用户的记录作为模板。
2. 等待创建结果返回
3. `notion_update_page`（update_properties）填：

```json
{
  "行程": "<旅行名称> | <YYYY年MM月DD日> | <出发地> ‣ <目的地> | Day <N>",
  "行程日": "Day <N>",
  "旅行": ["<旅行页面URL>"],
  "出发地": "<出发地>",
  "目的地": "<目的地>",
  "完成？": "__NO__",
  "景点": null
}
```

新页面只写本次记录明确提供的值；未提供的可选字段留空，不沿用其他记录的属性或正文。
- `景点` → null（旧行程关联的景点）
- `完成？` → `__NO__`（默认未完成）

#### 3. 验证

fetch 最后一条行程，确认：
- parent-data-source = 行程
- 行程标题、行程日、关联旅行正确
- 景点已清空

向用户报告：共创建了 Day 1 ~ Day N 共 N 条行程，出发地→目的地路线。

## 场景三：排景点（在某天行程下创建地点）

行程排好后，用户告诉某天要去哪些地方，自动创建地点记录并排好第几站。

### 触发条件

- "Day 1 先去洪崖洞，然后吃火锅"
- "第一天行程：上午博物馆，下午步行街，晚上吃烧烤"
- 发一张攻略图/截图，说"按这个排 Day 2"

### 输入解析

从用户话里提取：
- **第几天**："Day 1 / 第一天 / 1号那天"
- **地点列表**：按出现顺序，依次是第 1 站、第 2 站、第 3 站...
- **每个地点的类型**：根据名称自动判断（见下表）

### 类型自动判断

| 用户说的词 | 类型 |
|---|---|
| 博物馆、寺庙、公园、景区、纪念馆、古迹、古镇、洪崖洞、磁器口 | 景点 |
| 火锅、餐厅、小吃、早茶、烧烤、面馆、大排档、咖啡店 | 美食 |
| 商场、步行街、奥特莱斯、夜市、购物中心、商圈 | 购物 |
| 演唱会、相声、脱口秀、评弹、演出、音乐会 | 演出 |
| 游乐园、主题乐园、漂流、温泉、索道、游船、体验 | 体验 |
| 酒店、民宿、宾馆、威斯汀、洲际 | 住宿 |
| 机场、高铁站、火车站、码头 | 交通 |

判断不准时选最接近的，在报告里说明让用户确认。

### 执行流程

#### 1. 找到对应旅行和当天行程

1. 用 `notion_ai_search` 或 SQL 找到状态=计划中的旅行
2. 在行程库里按 `旅行` 关联 + `行程日`=Day N 找到当天的行程记录
3. 拿到旅行页面 URL 和当天行程页面 URL

#### 2. 逐个创建地点

对每个地点（按出现顺序，第几站从 1 开始递增）：

1. 在 Runtime 已解析的用户 Data Source 中直接创建新记录，不以其他用户的记录作为模板。
2. 等待创建结果返回
3. `notion_update_page`（update_properties）填：

```json
{
  "地点": "<地点名称>",
  "类型": "<类型>",
  "状态": "已安排",
  "旅行": ["<旅行页面URL>"],
  "行程": "<当天行程页面URL>",
  "第几站？": "<N>",
  "date:实际日期:start": null,
  "评分(满分10分)": null,
  "评价": null,
  "照片": null
}
```

新页面只写本次记录明确提供的值；未提供的可选字段留空，不沿用其他记录的属性或正文。
- `评分(满分10分)` → null（某个地点的评分）
- `评价` → null（旧评价文字）
- `照片` → null（旧照片）
- `date:实际日期:start` → null（还没去）

#### 3. 验证

fetch 最后创建的地点，确认：
- parent-data-source = 地点
- 类型、第几站、关联行程、关联旅行正确
- 评分/评价/照片已清空

向用户报告：Day N 排了 N 个地点，按顺序是：1. XX → 2. XX → 3. XX。

## 场景四：出行打卡

用户在旅途中说"到了XX"、"去了XX"、"XX打卡"，更新地点状态。

### 执行

1. 用 `notion_ai_search` 在地点库搜用户说的地点名
2. 找到后 `notion_update_page`：
   - `状态` = "已出行"
   - `date:实际日期:start` = 今天日期（is_datetime=0）
3. 如果用户说了评价（"人巨多"、"很好玩"），同时填 `评价` = 用户原话
4. 如果用户说了分数（"给7分"），同时填 `评分(满分10分)` = 数字

**没找到地点记录** → 问用户是不是在排行程时漏了，要不要新建。

## 场景五：每日行程完成

用户说"今天行程结束了"、"Day 1 搞定了"。

### 执行

1. 找到对应旅行的当天行程记录（行程日 = Day N）
2. `notion_update_page`：`完成？` = `__YES__`

## 场景六：旅行结束复盘

用户说"旅行结束了"、"回来了"、"重庆行圆满结束"。

### 执行

1. 找到对应旅行记录
2. `notion_update_page`：
   - `状态` = "已出行"
3. 如果用户给了整体评价（"这次旅行很满意"、"太累了"）：
   - 根据语气推断星级：很满意/超值 → 🌟🌟🌟🌟🌟；不错 → 🌟🌟🌟🌟；一般 → 🌟🌟🌟；一般般 → 🌟🌟；不推荐 → 🌟
   - 填 `旅行评价` = 对应星级选项
4. 如果用户明确说几颗星，按用户说的填

## 场景七：给地点补照片

用户说"XX没拍照，帮我加张照片"、"给芳草街传张图"。

### 执行

1. `notion_ai_search` 在地点库搜地点名
2. 找到后：
   - `image_search` 搜 `"<地点名>" 照片 风景 高清`
   - 追踪直链 → `notion_create_attachment` → `file_upload_id`
   - `notion_update_page`：`照片` = `[{"type":"file_upload","file_upload":{"id":"<file_upload_id>"}}]`
3. 告诉用户已补上

## 场景八：多城市移动

用户描述中间怎么换城市，修改对应天的行程路线。

### 执行

1. 找到对应旅行
2. 用户说"Day 3 从成都去重庆"：
   - 找到 Day 3 行程记录
   - `notion_update_page`：
     - `出发地` = "成都"
     - `目的地` = "重庆"
     - `行程`（标题）= 重新拼：`<旅行名> | <日期> | 成都 ‣ 重庆 | Day 3`
3. 如果用户说"Day 4 还在重庆"，就把 Day 4 的出发地和目的地都改成"重庆"
4. 以此类推，按用户说的移动链调整每一天

> 默认排行程时中间天都是"目的地→目的地"，用户说换城市后逐天改。

## 场景九：临时加地点

旅行中或规划后临时加一个地方。

### 执行

1. 用户说"Day 2 临时加一个宽窄巷子"
2. 找到 Day 2 行程记录
3. 查当天已有的地点，找到最大的第几站编号，新地点 = 最大编号+1
4. 在 Runtime 解析出的地点 Data Source 中新建地点记录，按实时 Schema 填入：
   - `地点` = 用户说的名字
   - `类型` = 自动判断
   - `状态` = "已安排"（或出行中打卡时直接"已出行"+今天日期）
   - `旅行` = 当前旅行 URL
   - `行程` = 当天行程 URL
   - `第几站？` = 新编号

## 场景十：取消或修改旅行

- **取消**：用户说"XX不去了"、"取消这次旅行" → 找到旅行记录，`状态` = "取消/放弃"
- **修改**：用户说"出发时间改到10月3号"、"添加同行人" → 找到旅行记录，update 对应属性

## 场景十一：旅行支出关联

用户在旅行期间记账时（"今天午饭花了50"、"住宿300块"），除了正常走 expense-tracker 流程，额外把这笔支出关联到当前进行中的旅行记录：

1. 找到状态=出行中 或 计划中的旅行
2. 在新建支出记录后，更新旅行记录的 `支出` relation，把新支出页面 URL 追加进去

> 如果同时有多个进行中的旅行，问用户这笔钱属于哪个旅行。

## 不碰

- **旅行评价**：用户复盘时自己打星
- **Place**（地理位置）：用户在 Notion 地图视图手动选
- **公式字段**（旅行信息、星级评分、颜色展示、概览、已结束）：Notion 自动算
