# SOP 构建

## 目标

把真实实践中已经有效的做法、隐性判断和重复经验，整理成下一次能够稳定执行、检查和迭代的流程。

坚持最高原则：

> 不要替用户发明一套看起来完整的 SOP；优先把现实里已经有效的做法真正说清楚。

只负责：识别、提取、结构化、固化。

## 守住边界

不要把以下需求伪装成 SOP 构建：

- 从未实践过的事情：转向学习、研究、实验或项目设计。
- 尚未澄清的问题：先澄清问题。
- 一次性或高度探索性的任务：用项目或任务管理。
- 对已完成行动的复盘：先复盘；稳定经验出现后再沉淀。
- 通用最佳实践搜索：明确作为外部建议，不写成用户已验证的流程。
- Skill 或 Automation 开发：只判断升级潜力，不顺手开发。

如果目前不适合 SOP 化，直接说明原因以及还缺什么现实验证，不要为了交付文档而硬生成。

## 按证据优先

按以下顺序使用信息：

1. 用户真实执行过的流程、当前事实和原始记录
2. 当前 Project、复盘或实际执行产生的经验
3. 已有 SOP 和用户明确的系统规则
4. 用户在对话中补充的隐性判断
5. [sop-patterns.md](references/sop-patterns.md) 中的结构模式
6. AI 通用经验

只把前四层当作用户流程证据。把 AI 通用经验明确标为“建议”或“待验证项”，先征得用户认可，再并入正式 SOP。

需要个人系统上下文时，云端 Notion 是唯一的个人资料源。不要要求或读取本地导出、同步副本、Markdown 镜像、静态索引或缓存来补充个人事实；云端不可用时说明缺口，不回退本地。

## AI 人生系统索引

需要读取已有 SOP、项目或复盘时，先调用 `$ai-life-system-init` 的 `scripts/runtime.py status`，再用 `resolve --concept sop` 定位真实`SOP流程`数据源；其他证据源只按本轮实际需要解析。

- `needs_init` 时引导用户运行 `$ai-life-system-init`，不回退固定 ID。
- `multiple` 不静默取第一个；结合用户指定页面或当前实践消歧。
- 本地索引只负责结构路由，实践证据仍从云端 Notion 实时读取。
- 用户明确要求保存或更新时，把本次目标、字段和选项传给 `check-write`；通过后仍须检查实时 Schema、同名 SOP 和写后结果。

## 先过 SOP Worthiness Gate

综合判断：

- 是否会重复发生
- 目标是否相对稳定
- 输入和输出是否相对稳定
- 是否已有现实经验
- 标准化是否能降低成本、错误或认知负担

不要机械打分。满足得越充分，越适合固化。

以下情况通常不适合：

- 一次性任务
- 人生方向探索
- 纯创意发散
- 原因尚未搞清的问题
- 每次条件完全不同的复杂判断
- 完全没有实践证据的新活动

若只有少量真实经验但值得继续验证，可在用户明确同意后形成“试用版 SOP”，并把未验证部分清楚标出；不要称为成熟流程。

## 执行五步工作流

内部遵循：

> Reality → Extract → Structure → Harden → Publish  
> 现实 → 提取 → 结构 → 加固 → 固化

不要把这五个英文阶段反复讲给用户。让它们指导工作即可。

### 1. Reality：回到真实场景

优先复用当前对话、Notion 中的相关 Project/复盘/已有 SOP、用户提供的案例和执行记录。信息足够时直接整理，不重复提问。

信息不足时，只补高价值缺口：

- 最近一次实际上是怎么做的？
- 什么时候启动这套流程？
- 哪一步最关键或最容易出错？
- 最后什么样才算完成？

一次只问一个最能推进的问题。

### 2. Extract：提取有效做法和隐性判断

从真实叙述中找出：

- 显性动作
- 输入和产出
- 隐性判断
- 关键经验
- 过去踩坑
- 停止、返回或升级条件

重点追问：

- 你做这一步时，脑子里实际在判断什么？
- 你怎么知道这样做是对的？
- 新人最容易误解哪里？
- 哪些经验你每次都会用，但从来没有写出来？

不要满足于“整理内容、优化一下、检查质量”等模糊动作。

### 3. Structure：形成最小可执行结构

只结构化到足够稳定执行的程度。对关键步骤尽量明确：

> 什么时候进入 → 做什么 → 得到什么 → 怎样知道可以继续或结束

也就是：

> Trigger → Action → Output → Exit

简单流程保持简单。复杂流程再增加分支、返回、停止或下游 SOP。

需要选择结构时读取 [sop-patterns.md](references/sop-patterns.md)。模式只作为内部组织工具，不要求用户维护分类。

### 4. Harden：只加固容易失败的地方

让复杂度跟随现实风险：

- 容易遗漏：添加 Checklist
- 容易判断错：添加判断标准或好坏样例
- 经常返工：添加验收标准
- 存在明显分支：添加 Exception
- 容易启动不了：添加最小启动动作
- 某一步决定结果：标出 Critical Step

不要给所有步骤强塞工具、负责人、时间、风险、异常和质量字段。需要判断 SOP 边界或加固程度时读取 [sop-principles.md](references/sop-principles.md)。

### 5. Publish：形成可用 SOP

默认只生成或优化，不写入 Notion。

统一使用以下骨架，并按真实复杂度自然补充必要内容：

```markdown
<aside>

**目的**

...

**预期成果**

...

</aside>

### 1. 准备工作

---

#### 定义：

...

#### 工具：

...

#### 前置条件

- [ ]

### 2. 执行步骤

---

- [ ]

...

### 3. 完成

---

1.
2.
```

把分支、检查项、失败信号和关键标准放在相关步骤下面。把最终验收和结束动作放在“完成”。不要因为结构模式不同而发明另一套页面模板。

## 控制对话

- 先利用已有证据，再提问。
- 信息足够时直接给出初稿，不走固定轮次。
- 信息不足时一次只问一个关键问题，并简要说明为什么需要它。
- 保留用户经过验证的原话和判断，不擅自改成通用管理术语。
- 清楚区分“用户已验证”“从记录推断”“AI 建议”。
- 用户要求轻量版时压缩表达，不删掉关键判断和完成标准。
- 用户要求优化已有 SOP 时，先读取现有内容，指出保留、修改和待验证部分，再输出完整新版。

## 写入 Notion

只有用户明确说“保存到 SOP”“写进 Notion”“更新这个 SOP”等写入指令时才执行。

写入前：

1. 在当前 Notion 云端搜索真实的“SOP流程”数据库。
2. 获取数据库、数据源 Schema 和当前默认模板。
3. 搜索同名或实质相同的 SOP，避免重复。
4. 更新时读取原页面；新建时确认用户确实要求创建。

写入时：

- 使用运行时真实字段，不写死数据库 ID、字段清单或选项。
- 把“目的、预期成果、启动条件”等放在当前模板要求的位置；只有 Schema 中确实存在对应属性时才写属性。
- 不主动创建数据库、字段、Relation、版本系统或维护机制。
- 不执行 Notion 按钮。
- 若用户已有版本结构，只按现有规则或明确要求使用。
- 关系字段只在目标已核实且关联确有意义时填写。

写入后重新读取页面，确认标题、属性和正文已经落地。Schema 无法验证时保留生成结果并说明阻塞，不猜字段。

## 判断是否值得升级

完成 SOP 后在内部判断：

- 低频、仍在变化或高度依赖人的判断：留在 Notion SOP。
- 高频、稳定、专业判断可以表达且会跨场景调用：可建议成为 Skill 候选。
- 高频、稳定、输入输出明确且判断基本确定：可建议成为 Automation 候选。

只在升级潜力明显或用户询问时简短提出。不要在本 Skill 中开始开发。

## 完成标准

交付前确认：

- 知道什么时候启动
- 知道按什么顺序做
- 关键步骤包含真正影响结果的判断
- 知道每一步或关键阶段产出什么
- 知道做到什么程度可以结束
- 高风险处已有必要的检查、验收或异常处理
- 没有把 AI 建议伪装成用户已验证经验
- 文档足够轻，下一次可以直接使用

完成的标准不是文档看起来完整，而是用户下次遇到相同场景时真的能执行。
