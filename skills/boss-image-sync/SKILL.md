# Boss 图同步

为用户选定范围内的目标卡片匹配合适的 Boss 图。根据目标主题色判断现图是否合适，保留匹配的图，为不匹配或缺图的目标提出候选，并在用户确认后更新。用户明确要求全部重配时，才重新评估并替换已匹配的图片。

## Notion 结构与写入边界

本 Skill 使用 `$ai-life-system-init` 作为 Notion 运行时底座：

1. 运行 `scripts/runtime.py status`；若为 `needs_init`，引导用户运行 `$ai-life-system-init`。
2. 用 `scripts/runtime.py resolve --concept goal` 定位用户自己的目标 Data Source。只有 concept 未匹配时才尝试 `resolve --source "目标"`，不得猜测或复用固定 ID。
3. 读取实时 Schema，找到目标记录中代表 Boss 图片的可写文件属性。默认用 `resolve --property "Boss图"` 查找；若不存在或候选有歧义，从 Schema 中辨认图片/文件属性，必要时询问用户，不把名称当成模板契约。
4. 只读取用户请求范围内的目标和判断所需的少量关联数据。若用户要求处理全部目标，优先处理当前有效目标；使用实时状态字段排除已完成或归档项。结构不支持判断时，向用户说明范围并确认。
5. 每次更新前，对目标 Data Source 和本次图片字段运行 `scripts/runtime.py check-write --operation update`。重新检查 Notion 实时 Schema 与目标页面，写后回读确认。

只修改确认过的图片字段，不改目标名称、状态、领域关系、正文或其他属性。Runtime 预检不等于用户确认图片或授权替换。

## 判定每个目标的主题色

优先级如下：

1. 用户直接指定的颜色或主题。
2. 目标自身 Schema 中明确可读的颜色/主题属性，包含公式可读结果。
3. 目标与分类、领域或其他主题页面的真实 relation：先从 Schema 确认 relation 指向的 Data Source，再读取相关页面中明确的颜色/主题属性。
4. 目标自身明确的图标或页面视觉颜色。

只采用能从当前 Notion 结构或用户说明中确认的线索。Formula 值或关联页面不可读、relation 缺失、出现冲突颜色时，不以字段名、优先级或过往用户数据猜颜色；标记为待确认并询问用户。不要为推断颜色读取无关页面正文。

## 评估现有图片

1. 读取目标记录中已配置的图片，必要时用 Notion 返回的可访问文件 URL 获取图片供视觉检查。URL 可能是临时授权链接，不得记录到 Skill、聊天或共享文件中。
2. 判断图片整体主色、主体辨识度及其与目标主题色的契合程度。文件名无法证明图像内容；如果图片无法查看，标记为无法评估，不直接替换。
3. 将每个目标分类为保留、缺图、建议替换或需补充主题色；简要说明原因。
4. 在搜图前向用户汇报拟处理范围。默认保留现有匹配图，只为缺图或明显不匹配项找候选。

## 搜索候选

- 图源默认可以从《王者荣耀》《英雄联盟》等游戏作品中选择；用户指定其他作品时优先按其指定来源。不要假设每位用户都使用同一款游戏。
- 优先查找官方角色立绘、皮肤原画或正式宣传图，并保留可以核查的来源链接。第三方图片只有在用户接受该图源且来源可核实时才推荐；不要把非官方图描述成官方素材。
- 以主题色契合度、角色辨识度和裁切后适合作为卡片图为筛选标准。避免明显水印、错误角色名或无法验证出处的图片。
- 每个待处理目标给出 1–2 个候选及来源，并标注它们的主色和选择理由。等待用户确认具体候选与替换范围后，才开始上传。

## 上传、更新与验证

1. 使用当前 Notion 连接提供的文件上传能力上传用户确认的图片。优先用连接支持的直接来源 URL 或文件引用流程；不要把 Notion token、上传授权头或临时签名 URL 复制到命令行、聊天或 Skill 文件。
2. 更新前确认目标页面属于通过 Runtime 解析出的 Data Source，且实时文件属性仍可写。将上传结果映射到 Schema 中唯一匹配的图片字段。
3. 仅更新用户确认的图片属性；失败时保留现有属性，不清空旧图，不尝试修改其他记录。
4. 回读页面，核实父 Data Source、图片属性和新文件。上传、更新或回读有一步失败，就如实报告部分完成状态。

## 完成汇报

按目标汇报保留、替换、新增或待确认状态，并为已选图片附上来源链接。不要宣称图片来源、颜色或写入结果未经核实。
