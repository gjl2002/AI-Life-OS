# 用户画像云端写回

## 权限与事实来源

只写入 `$ai-life-system-init` Runtime 解析出的当前用户云端“用户画像”Data Source。Runtime 负责目标与字段预检，云端实时 Schema 和记录负责内容事实。

用户必须明确要求保存、更新或直接写入。`create_page_ready` 或 `write_ready` 只表示结构预检通过，不代表用户授权。

## 写入前

1. 运行 Runtime `status`。
2. 用 `resolve --concept user_profile` 解析唯一 Data Source。
3. 确认 `read_ready`，实时读取数据库 Schema。
4. 搜索现有记录，比较画像名称、JTBD、触发场景、购买逻辑、产品关系和证据，识别重复或可更新记录。
5. 完成证据审计、分群判断和质量检查。
6. 决定本次实际写入字段，再运行 Runtime `check-write`，显式传入所有字段与选项。

`multiple`、无法确认 Schema 或重复候选歧义时停止写入，不静默选择。

## 创建还是更新

优先更新已有记录：

- 新材料增强或修正同一 JTBD、触发和购买逻辑；
- 假设画像获得新的直接证据；
- 原话、抗拒、信任因素或适用边界需要补充；
- 原记录已经过时，但仍代表同一用户类型。

只有以下情况才新建：

- 没有现有画像能够代表该群体；
- 新材料揭示了会改变定位、产品或销售决策的不同 JTBD、触发或购买逻辑；
- 用户明确要求创建独立记录，且不会制造明显重复。

不要因为人口属性不同就创建新画像。

## 字段与正文

只使用实时 Schema 中实际存在且 Runtime 允许写入的字段。不要在 Skill 中保存字段名单，也不要根据旧模板猜测属性。

- 能准确映射的短信息写入现有属性；
- 用户原话、场景、购买逻辑、事实/洞察/假设、证据来源、分群边界和验证缺口写入页面正文；
- relation 目标必须解析唯一并通过写入预检；
- Schema 没有对应字段时保留在正文，不自动修改数据库结构。

更新现有记录时保留仍有效内容，只替换或追加本次明确校准的章节，不覆盖无关正文。

## 写入后

回读记录并核对：

- 标题与画像类型；
- JTBD 和触发场景；
- 用户原话及来源；
- 为什么购买、为什么不购买、什么建立信任；
- 已确认事实、合理洞察与待验证假设；
- 证据来源与下一步验证；
- relation 是否指向预期对象。

核对失败时只修复本次写入范围并再次回读。

## 禁止写入

- 只有业务定位、产品文档、理论或竞品材料，却被包装成正式用户事实；
- 没有可追溯用户声音的正式画像；
- 重复候选仍然无法消歧；
- 证据审计或质量检查仍有阻塞项；
- 用户尚未授权。
