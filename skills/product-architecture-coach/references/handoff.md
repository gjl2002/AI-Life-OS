# Handoff Rules

Use this reference to decide what should happen after 产品架构教练 finishes.

## To `$product-opportunity-coach`

Return to `$product-opportunity-coach` when:

- first buyer is unclear
- trigger scene is unclear
- substitute or competitor is unknown
- demand has not been validated
- price claims rely on weak evidence
- the product may be too broad to test

Provide:

- proposed product shape
- key assumptions
- first validation object
- risk that needs evidence

## To `$product-experience-coach`

Use `$product-experience-coach` when:

- the architecture is accepted
- the user needs onboarding, activation, retention, drop-off repair, service blueprint, peak/end design, or feedback cadence
- the product is a training camp, service, consulting offer, or community with real operations

Provide:

- stages
- user tasks
- touchpoints
- deliverables
- feedback needs
- provider workload assumptions

## To `$product-detail-page-design`

Use `$product-detail-page-design` when:

- product promise, structure, deliverables, price, proof, and CTA are mostly clear
- the user needs a long landing page, product detail page, or multi-image sales page

Provide:

- value point
- solution
- payment reason
- proof available
- missing proof
- claim-risk notes
- pricing logic
- CTA/testing action

## To `$course-handout-writing-coach`

Use `$course-handout-writing-coach` when:

- stages and lessons are stable
- each lesson has a clear problem, method, task, and deliverable
- the user wants full teaching copy, manuals, worksheets, or scripts

Provide:

- course structure
- lesson briefs
- target student
- tone
- examples to include
- assignment and self-check rules

Do not write full handouts while core architecture is still changing.
