# Teaching PPT Rhythm

Internal teaching-design reference derived from a 13-lesson benchmark deck corpus and its matching transcripts. Use the mechanisms, never copy the source's wording, visual assets, cases, or commercial claims.

## First distinction: slide design vs. live demonstration

A recorded lesson can contain three visual layers:

1. **Designed teaching slide**: a deliberate visual statement, framework, contrast, or task.
2. **Evidence slide**: a designed canvas that frames a real case, output, or source image.
3. **Live demonstration**: a full-screen tool, system, website, or workflow operation.

Do not mistake a screen recording for PPT design. Plan it as a separate delivery beat with a clear before-demo question and after-demo takeaway.

## The slide is a speaking surface, not a handout

The purpose of a slide is to control attention while the teacher explains. It should usually carry one of these jobs:

| Page role | What it does | On-screen form |
| --- | --- | --- |
| Chapter/title | mark a new mental territory | minimal title |
| Tension/question | make the learner notice a problem | one large question or contrast |
| Core judgment | state the new frame | one sentence, emphasized keywords |
| Structure | make relationships visible | 2-5 nodes, sequence, loop, matrix, or split comparison |
| Contrast | correct an old interpretation | wrong/right, before/after, shallow/deep |
| Evidence | make a claim credible | one real case, screenshot, result, or annotated artifact |
| Action | tell the learner what to do now | short steps, task, submission requirement |
| Bridge | close a thought and prepare the next one | summary judgment or next question |

Avoid slides that try to do all jobs at once.

## Visual language extracted from the corpus

The recurring black-canvas system is functional:

- black ground removes decoration and creates a teaching stage;
- large white text carries the main judgment;
- gray is secondary context;
- red is used sparingly for a risk, misconception, or rejected choice;
- green is used sparingly for a validated action or recommended direction;
- thin white/gray lines and small numbered nodes show sequence or relationship;
- screenshots are usually isolated on the black canvas rather than turned into dense collages;
- repeated typography, alignment, and node style lower orientation cost across a long live session.

This is not a requirement to use black slides. When adapting, preserve the *attention hierarchy* and role clarity, not the surface palette.

## Default lesson rhythm

For a teaching block, alternate between verbal and visual modes:

```text
question / tension
-> core judgment
-> structure
-> case or proof
-> method steps
-> live demonstration when needed
-> action / task
-> bridge
```

Do not show a framework and leave it on screen for the whole explanation. Re-state the logic through a case, a decision point, or an observable action. This creates the feeling of moving downward rather than merely listing concepts.

## Micro-rhythm for one idea

Use a 4-6 beat sequence when one idea needs depth:

1. `What seems to be the problem?` — learner scene.
2. `What is actually happening?` — core judgment / root mechanism.
3. `What does that change?` — a visual relationship or contrast.
4. `How do we act on it?` — method steps and decision criteria.
5. `What does it look like in reality?` — case, evidence, or demo.
6. `What will you produce now?` — task and artifact.

Not every idea needs six slides. A simple idea may use one; a threshold concept may need the full sequence.

## Framework design rules

Use a framework slide only when it reduces cognitive load.

- Keep the number of first-level elements low enough to say aloud in one breath.
- Build the diagram around a relationship: sequence, cause, choice, feedback loop, or layers.
- Put short labels on the nodes; place explanation in the speaker's words or a following page.
- Reveal or revisit the same framework when the narrative moves to a new layer.
- Prefer one structure per slide over a large “everything map”.

## Screenshot and demo rules

- A screenshot must prove, clarify, or enable an action; it is not generic decoration.
- Precede it with the question the learner should inspect, then narrate the relevant area.
- After a live demo, return to a designed slide that names the reusable rule; otherwise the learner remembers clicks rather than method.
- Separate `PPT node` and `live demo node` in the lesson plan.

## PPT planning fields

For each planned slide or beat, record:

| Field | Requirement |
| --- | --- |
| Slide role | choose from the page-role table |
| On-screen sentence | one sentence or label the learner must retain |
| Spoken purpose | what the teacher explains beyond the slide |
| Evidence/asset | real case, system view, or none |
| Transition | what question this page answers or opens |

This prevents a deck from becoming a transcript pasted onto pages.

## Final review

Before presenting, check:

1. Does every slide have one dominant teaching job?
2. Can a learner identify the main judgment at a glance?
3. Are diagrams relationship-first rather than decorative?
4. Are screenshots framed as evidence or demonstrations, not mistaken for the design system?
5. Does the deck alternate explanation, structure, proof, and action often enough to prevent passive listening?
6. Does every live demonstration end with a reusable rule and a learner action?
