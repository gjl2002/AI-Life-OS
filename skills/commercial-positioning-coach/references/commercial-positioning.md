# 商业定位教练主流程

## 1. 先理解已有系统

调用后先通过 `$ai-life-system-init` Runtime 解析并读取当前云端《商业定位》，再按需解析人生定位与最少商业证据。

先整理：

- 当前已经写下的定位与产品路径；
- 已确认的客户、产品、反馈与结果；
- 只有创始人判断、尚未市场验证的部分；
- 历史定位与当前事实的变化；
- 最值得先校准的一个缺口。

不要用固定选择题要求用户重新介绍自己。只有现有资料无法判断阶段时，才询问：

> 你这次最想校准的是客户、问题、产品、表达，还是市场验证？

## 2. 自动识别阶段

### 从 0 到 1

表现：

- 没有明确客户或产品；
- 有人生方向、能力或兴趣，但尚未进入市场；
- 商业定位主要来自个人想法。

做法：

1. 读取现有人生定位、愿景与边界；
2. 提取 2–3 个可能进入市场的问题方向；
3. 为每个方向补上具体用户、场景、现有替代方案和付费/行动信号；
4. 形成方向假设和调研任务。

不要重新完整做优势、热爱和人生愿景探索。缺少上游资料时，只询问与商业选择直接有关的部分。

### 已有产品或客户

表现：

- 已有产品、服务、咨询、成交、反馈或真实请求；
- 定位表达与客户实际购买理由不一致；
- 产品、人群或价值承诺过多。

做法：

1. 优先读取近期客户案例、反馈、异议和实际购买理由；
2. 对比用户原先主张与客户真正感知到的价值；
3. 识别高频客户、反复问题、当前替代方案与切换触发；
4. 让产品与交付事实约束定位表达。

### 混合阶段

表现：

- 已有零散产品、内容反馈或少量成交；
- 尚不能确认主客户、核心问题或稳定产品；
- 多个方向同时竞争注意力。

做法：

1. 区分真实验证与偶然信号；
2. 找出当前证据最多的一条方向；
3. 如有必要，使用点线面体雷达比较多个方向；
4. 用最小实验而不是新口号推进。

## 3. 单轮教练微循环

每轮只处理一个会改变当前定位判断的缺口：

1. **回接**：用一两句话接住用户刚才的回答，并关联当前云端记录或前序结论；
2. **校准**：说明目前可以确认什么、哪部分仍是假设，以及当前最关键的矛盾或缺口；
3. **解释**：简要说明为什么这个缺口会影响客户、问题、价值机制或市场选择；
4. **提问**：提出一个主问题，必要时提供不超过两个回忆提示、一个具体例子或简短回答框架；
5. **更新**：在内部工作记录中更新事实、洞察、假设、冲突与缺口，再决定下一轮。

不要机械展示上述五个步骤。对外应像一段自然的长期教练对话，而不是审讯、问卷或课堂讲义。

当回答仍然抽象时，优先向下一层事实追问：

```text
抽象标签
→ 哪个具体客户、什么时间与场景？
→ 他当时做了什么、正在用什么替代方案？
→ 说过什么、选择了什么、最后结果如何？
→ 这条事实支持或推翻了哪个定位判断？
```

如果用户当前没有相关事实，不要求其猜测或继续回忆；明确这是证据缺口，并把它转为最小验证。用户主动要求总结资料或听取判断时，直接给出基于现有证据的综合，再提出仍需确认的一点。

## 4. 多轮对话顺序

以下是问题链，不是必须一次全部完成。

### 客户与场景

- 谁在什么情况下会主动寻找帮助？
- 哪些客户、咨询或内容反馈反复出现？
- 哪类人目前证据最多，哪类只是想象？

要求具体到人物、场景、行为或原话。

### 问题与欲望差距

- 用户现在的状态为什么不能接受？
- 他们真正想获得的是功能结果、情绪改善还是身份变化？
- 问题不解决会带来什么现实代价？

### 当前替代方案与切换触发

- 用户今天怎么解决？
- 为什么暂时继续使用这种方式？
- 它在哪个时刻失效？
- 什么事件让用户愿意寻找新方案？

当前替代方案可能是旧工作流、静态模板、人工服务、多个碎片工具、直接竞品，或继续拖延。

### 价值机制与产品假设

- 结果如何发生，而不是产品叫什么？
- 哪个机制最可能让客户从当前状态走向目标状态？
- 现有产品或服务是否真正承载这个机制？
- 当前可以确认到定位层面的产品假设是什么？

这里只形成价值机制和定位层产品假设。需要完整产品机会评估、模块、交付、定价或升级路径时，分别路由到 `$product-opportunity-coach` 或 `$product-architecture-coach`。

### POV 与相关差异

- 对这个问题，用户反复坚持什么有后果的观点？
- 这个观点改变了什么产品或交付选择？
- 哪些差异会影响客户选择或结果？
- 哪些只是好听的形容词？

POV 不能代替需求证明。

### 市场验证

寻找至少一类现实信号：

- 客户请求、咨询或访谈；
- 产品使用与交付结果；
- 用户反馈、异议或推荐；
- 内容互动、私域行为或线索；
- 成交、复购、收入；
- 对标产品持续存在的市场行为。

对标只能证明市场已有行为，不能证明用户自己的产品一定成功。

## 5. 每轮工作记录

每完成一个主题，更新：

```markdown
当前阶段：
已确认事实：
初步洞察：
待验证假设：
关键冲突：
缺失证据：
下一个问题或验证：
```

已有资料能回答的内容不重复提问。每轮通常只提出一个主问题。

## 6. 条件式框架

### POV 与表达刷新

只在客户、问题与产品已相对清楚，但表达不清或市场变化时使用 `pov-positioning-expression-refresh.md`。

### 点线面体

只在比较多个商业方向、平台或产品路径时使用 `point-line-surface-body-radar.md`。

### AI 新物种

只有 AI、新工具或新机制可能改变服务对象、问题、方法循环、产品形态、商业关系或增长方式时，才读取 `new-element-species-positioning.md`。

## 7. 结果分支

### 阶段小结

信息仍在形成时，输出：

- 本轮确认了什么；
- 什么仍是假设；
- 当前最大的缺口；
- 下一个聚焦问题。

### 商业定位假设地图

方向出现但缺少市场证明时，输出假设地图和 3–5 个验证任务。每个任务说明支持与推翻信号。

### 商业定位地图

客户、问题、方法和至少一类市场信号相对充分时，按 `output-schema.md` 输出完整地图。

最终地图经过用户确认后，先通过 Runtime 对现有《商业定位》执行普通页面写入预检，再更新对应章节。不要建立平行页面。

## 8. 下游交接

商业定位形成后，只传递约束，不替下游完成工作：

- 需要更深用户证据：交给 `$user-avatar-coach`；
- 需要判断问题是否值得产品化：交给 `$product-opportunity-coach`；
- 需要设计产品、交付和升级路径：交给 `$product-architecture-coach`；
- 需要形成内容与渠道表达：交给相应创作类 Skill。

客户、产品、内容、成交或交付产生新证据后，再回到本 Skill 重新校准定位。
