# 用户画像教练工作流

## 1. 明确本次研究对象

从用户请求和现有资料判断属于哪一种：

- 新画像：从真实材料中识别一个或多个用户类型；
- 更新画像：用新证据增强、修正、合并或拆分已有画像；
- 产品专项：研究某个产品、服务、课程或 Offer 的用户与买家；
- 批量分群：聚类一批访谈、聊天、评论、问卷或反馈；
- 访谈准备：证据不足，设计下一轮最有价值的研究问题。

只有目标无法从用户材料和云端上下文判断时才提问。产品专项要先确认研究的是使用者、购买者还是两者。

## 2. 读取最少背景

按 `source-routing.md` 通过 Runtime 定位云端来源：

1. 检查已有用户画像，避免重复创建；
2. 读取商业定位，理解当前商业选择，但不把它当成用户事实；
3. 根据研究对象选择最相关的产品、客户沟通、用户反馈、客户管理或购买记录；
4. 用户明确指定的页面、记录或材料必须优先读取。

不全库扫描，也不全 Relation 扫描。先查看标题、描述、时间、摘要和关联，再决定是否读取正文。

## 3. 建立材料包

内部记录：

```markdown
研究对象：
研究时间范围：
用户身份或材料批次：
用户直接提供的材料：
选中的云端来源：
证据等级：
仍然缺少的材料：
```

同一条材料要能追溯到具体访谈、聊天、页面、截图或记录。无法确认是否来自同一个用户时，不把多条材料合并成完整个人经历。

## 4. 提取用户声音与行为

保留会影响判断的原话或近义转述，并标记来源。为每条关键信号提取：

- 发生场景与触发事件；
- 用户当时想完成的任务；
- 实际采取的行为；
- 当前替代方案与失败点；
- 想获得的结果；
- 购买或行动触发；
- 抗拒、未购买和放弃原因；
- 信任来源与风险顾虑；
- 产品使用和交付结果；
- 内容或表达触发。

遇到强情绪、赞美、投诉、犹豫、防御或言行冲突时，按 `empathy-radar.md` 解读；解读属于洞察或假设，不能冒充用户原话。

## 5. 聚类与保留冲突

合并重复信号，同时区分：

- 高频且跨用户出现的模式；
- 低频但会显著改变购买或交付的信号；
- 单个用户的特殊经历；
- 与商业定位一致的证据；
- 修正或反驳当前商业假设的证据；
- 当前无法解释的冲突。

不按材料顺序逐份摘要，也不让一个情绪强烈的故事自动代表所有用户。

## 6. 判断是否需要分群

只有差异会改变商业决策时才拆分画像。重点比较：

- JTBD 与期望进展；
- 触发场景；
- 当前替代方案；
- 购买动机与未购买原因；
- 信任要求；
- 价格、时间或隐私边界；
- 产品使用与交付场景。

只存在人口属性差异但购买和使用逻辑相同时，通常不拆分。必要时区分核心用户、次级用户、潜在但未验证用户和不适合用户。

## 7. 决定产物类型

- 只有部分信号，还在确认研究对象：阶段小结；
- 缺少 Level 1 或强 Level 2 证据：用户画像假设；
- 多份真实用户材料形成重复模式，且购买逻辑可追溯：正式用户画像；
- 多群体差异会改变定位、产品或销售：分群画像。

正式画像和重要分群先运行 `evidence-audit.md`，再按 `review-checklist.md` 审查。

## 8. 研究式对话

有材料时先分析，再提出一个最重要的缺口。每轮自然采用：

```text
回接已有证据
→ 说明目前能确认什么、不能确认什么
→ 解释这个缺口为什么会改变画像
→ 提出一个具体问题或需要补充的一类材料
```

抽象回答沿着“最近一次具体场景 → 行为与替代方案 → 原话或选择 → 结果”追问。确认用户没有相关证据后，不继续盘问，改为访谈或验证设计。

## 9. 输出与交接

按 `avatar-output-schema.md` 输出。只说明用户证据对以下环节的约束：

- 商业定位需要保留或修正什么；
- 产品 Agent 需要继续验证什么；
- 内容与销售表达应使用或避免什么用户语言；
- 哪个下游 Skill 应接手。

不在本 Skill 中完成完整商业定位、产品架构、内容计划、销售页或销售 SOP。

用户明确要求写回时才读取 `notion-writeback.md` 并操作云端。
