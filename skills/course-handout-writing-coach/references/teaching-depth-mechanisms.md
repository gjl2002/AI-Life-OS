# Teaching Depth Mechanisms

Internal teaching-design reference distilled from a 13-lesson benchmark corpus. Use the mechanisms, not its wording, stories, numerical claims, cases, assets, or commercial tactics as defaults.

## What makes a lesson feel deep

Depth is not more concepts. A deep lesson lets a learner see the full causal chain and act on it:

```text
desired result
-> current scene and costly misconception
-> root mechanism
-> method/path
-> decision criteria and boundaries
-> action/SOP
-> tool or system support
-> evidence, feedback, and iteration
```

Use only the layers that genuinely help the lesson. Do not manufacture a seven-part lecture.

## Required depth map

Before drafting a substantive lesson, fill this map in the lesson brief:

| Layer | Question to answer |
| --- | --- |
| Result | What concrete change does the learner want? |
| Scene | In what real situation does the learner feel the problem? |
| Misconception | What seemingly reasonable move keeps them stuck? |
| Mechanism | Why does that move fail? What causal relationship matters? |
| Path | What sequence moves them from current state to target state? |
| Boundary | For whom, when, and under what condition does this not apply? |
| Action | What can the learner do this week? |
| Asset | What template, system, prompt, worksheet, or SOP reduces execution friction? |
| Feedback | What signal proves progress, and how will they revise? |

If the mechanism, boundary, or feedback is unknown, label it as an assumption or research gap. Never cover the gap with certainty language.

## Speakable teaching arc

For a concept, method, or tool lesson, build a sequence that can be taught aloud:

1. Start with a recognizable scene, question, contrast, or failed attempt.
2. Name the learner's old interpretation without shaming them.
3. Reframe it with one core judgment.
4. Explain the causal chain: `because ... therefore ...`.
5. Show a counterexample, case, or before/after proof.
6. Turn the judgment into a method with decision points.
7. Demonstrate the method in a real tool, worksheet, or system where appropriate.
8. Give one bounded action and specify its deliverable.
9. Close by returning to the opening problem and bridge to the next lesson.

Use questions to surface the learner's thinking, then answer them with reasoning. Avoid rhetorical questions that add no decision value.

## Three teaching layers

Every core module should make its level explicit:

| Layer | Function | Typical output |
| --- | --- | --- |
| Logic | Explain why the issue exists and what really matters | a changed judgment |
| Method | Explain the path, sequence, and choices | a decision framework or SOP |
| Execution | Make the next action easier and observable | a filled worksheet, tool output, template, or system page |

Tools are not the lesson's protagonist. They make the method executable. A lesson that gives a tool without a decision rule creates dependence; a lesson that gives theory without an asset creates inertia.

## Methods for making reasoning concrete

- Use contrast: old path vs. better path; superficial metric vs. real outcome; visible symptom vs. root constraint.
- Use decomposition: break a large outcome into variables, stages, or smaller actions before proposing a tool.
- Use sequence: clarify what must be true before the next move; avoid teaching advanced tactics before prerequisites.
- Use cases as proof: `starting condition -> action -> result -> transferable rule`, not as decoration.
- Use data or numbers only when they are sourced and relevant; otherwise use a qualitative decision rule.
- Use systems to preserve the workflow: capture -> plan -> do -> record -> review -> revise.

## Theory Is a Load-Bearing Beam, Not a Slide Category

Use a theory, research finding, or source model only when it changes the learner's causal understanding or improves a decision. Integrate it at the moment the lesson explains a failure mechanism, method sequence, demonstration, or boundary. Do not make an isolated `理论背书` section that interrupts the lesson arc.

For example, do not say `下面介绍延展心智理论`. When explaining why records, a system, and AI can matter together, first show the learner's experience: a person cannot reliably hold all past signals in working memory. Then explain the mechanism: when an external record is repeatedly available, connected to decisions, and used in a feedback loop, it becomes part of the person's practical thinking environment. Name the theory only if useful.

## Course-wide coherence

Each lesson must name:

- incoming artifact: what the learner brings from the previous lesson;
- outgoing artifact: what this lesson creates for the next one;
- prerequisite: what must already be true;
- operating rhythm: when the learner will repeat or review this action.

This prevents a course from becoming isolated good lessons instead of one solution path.

## Commercial-course boundary

For product, content, private-domain, or sales lessons, distinguish:

- universal teaching mechanisms: clarify problem, test assumptions, reduce action cost, collect feedback;
- context-dependent commercial tactics: pricing, channel rules, platform behavior, conversion scripts, traffic claims, and urgency designs.

Treat the latter as hypotheses to be validated in the learner's market and under applicable platform rules. Do not present them as universal facts or transfer manipulative tactics into the user's course by default.

## Final depth check

Before finalizing, ask:

1. Does the lesson explain why, not merely what?
2. Does it reveal a cause or decision rule the learner did not previously see?
3. Is there a real boundary, trade-off, or non-example?
4. Can the learner produce an observable artifact within the stated scope?
5. Does the asset make the action easier without replacing judgment?
6. Is there a feedback signal and a next revision move?
