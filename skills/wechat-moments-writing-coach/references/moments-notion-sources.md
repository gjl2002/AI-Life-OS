# 云端 Notion 来源路由

## 原则

朋友圈创作只通过 `$ai-life-system-init` 提供的当前 Runtime 访问用户的 Notion 系统。

- 不读取本地 Notion Sync。
- 不依赖本地数据库索引。
- 不保存数据库 ID、个人路径或固定属性名。
- 先解析概念和 schema，再查询记录。
- Relation 表示候选相关，不代表全部全文读取。

## 概念路由

| 需要回答的问题 | 优先概念 | 使用目的 |
|---|---|---|
| 近期发过什么、是否撞题、是否需要排期、账号既有语感 | `content` | 历史内容、当前队列、去重、写回目标候选 |
| 这条属于哪个账号、账号在说什么 | `account` | 账号语境和受众边界 |
| 是否符合当前商业方向 | `commercial_positioning` | 服务对象、问题、价值主张、差异化 |
| 产品事实和当前 offer | `product` | 功能、形式、价格、名额、截止、CTA |
| 目标用户是谁 | `user_profile` | 用户场景、痛点、期待与语言 |
| 有哪些可信反馈或结果 | `user_feedback` | 客户原话、效果证据、边界 |
| 客户真实怎么说 | `client_communication` | 问题措辞、异议和购买语境 |
| 是否需要客户关系背景 | `client_management` | 仅在授权且确有必要时读取 |
| 外部结构或内容参考 | `benchmark_content`、`benchmark_account` | 学习结构，不冒充个人事实 |
| 与当前行动/阶段有关的真实场景 | `goal`、`project`、`weekly_review` | 只在当前素材需要时读取 |
| 某本书带来的观点 | `book` | 仅在用户内容明确依赖该书时读取 |

## 最小资料包

### Quick

默认只用用户当前材料。只有用户询问“现在发合不合适”或需要历史去重时，才读取 `content`。

### Enhanced

按题材选择 1–3 个必要来源。例如：

- 专业判断：`content` + 必要的定位或现实项目证据
- 客户反馈：`user_feedback`，必要时加 `client_communication`
- 产品轻提及：`product` + `commercial_positioning`

### Strict

读取完成高风险核验所需的最小集合，通常可能包括 `content`、`commercial_positioning`、`product`，以及当前文案所引用的客户或个人证据。

### Campaign

先读取 `content` 当前队列，再按活动涉及的账号、商业定位、产品、客户证据分批读取。不要一次拉取所有关联内容。

## 查询顺序

1. 从 Runtime 解析概念目标。
2. 读取目标 schema 或普通页面结构。
3. 先用标题、摘要、时间、状态、账号、关系等轻量信息筛选。
4. 只展开真正可能改变当前文案判断的记录。
5. 记录来源作用：事实、用户经验、外部观点、风格样本或排期信息。
6. 缺少关键证据时明确缺口，不自动扩展为全库 Research。

## 候选素材记录格式

```markdown
素材名称
- 类型：用户本人经历 / 用户或私域证据 / 产品证据 / 知识模型 / 过往内容 / 对标内容 / 第三方案例
- 简介：
- 可用角度：
- 可公开性：
- 来源：
```

## 降级规则

- 非关键概念不可用：继续使用用户材料，并说明未获得哪类辅助上下文。
- 关键事实来源不可用：不输出确定性产品、客户或数据宣称。
- `content` 不可用但用户只要草稿：仍可生成草稿，但不声称已完成历史去重或排期判断。
- 用户要求写回而 `content` 不可写或 schema 未解析：停止写回，保留草稿并说明阻点。

## 真实性规则

- 不虚构个人故事，不把第三方案例写成第一人称。
- 客户结果、价格、截止时间、名额和产品承诺必须来自当前证据。
- 产品对外名称必须来自当前产品、商业定位或用户明确指令；不确定时使用诚实的类别描述或询问。
- 公开资料在工作笔记中保留完整身份，在正文中使用自然出处锚点。
- Enhanced、Strict、Campaign 在最终输出前执行上下文核验。
