# SOP 结构模式

## 目录

1. 顺序执行型
2. 判断 / 应对型
3. 总调度型
4. 检查型
5. 路由 / 自动化型
6. 组合原则

这些模式只帮助组织流程，不作为用户必须维护的分类。先选最简单的主模式，确有需要时再组合。

## 1. 顺序执行型

**适合**

内容发布、课程制作、固定交付等主干顺序稳定的流程。

**核心结构**

> 触发 → 准备 → A → B → C → 验收

**重点**

- 写清阶段产出和流转条件。
- 只在关键节点增加检查。
- 下游细节已有独立 SOP 时直接调用，不重复展开。

**常见风险**

- 把所有步骤写成同等重要。
- 强制固定阶段数量。
- 每一步都堆满工具和标准。

## 2. 判断 / 应对型

**适合**

售后服务、异常处理、故障排查和不同条件下采取不同动作的流程。

**核心结构**

> 收到事件 → 识别信号 → 如果 X 则 A / 如果 Y 则 B → 收尾

**重点**

- 使用可观察信号定义分支。
- 明确暂停、退出和升级条件。
- 对高风险判断保留人工确认。

**常见风险**

- 按人物标签分支，却没有客观信号。
- 只有正常路径，没有退出机制。
- 分支过多，执行者无法快速选择。

## 3. 总调度型

**适合**

自媒体全流程、客户全生命周期等需要串联多个成熟 SOP 的主流程。

**核心结构**

> 主流程阶段 → 阶段交付物 → 流转条件 → 调用下游 SOP

**重点**

- 讲清阶段目的、输入、交付物和流转。
- 保持总流程可扫描。
- 把专业细节留在下游 SOP。

**常见风险**

- 复制所有下游步骤，形成巨型文档。
- 下游 SOP 不存在却假装已经可以调用。
- 主流程和执行细则发生冲突。

## 4. 检查型

**适合**

发布前检查、交付验收、实验准备和容易遗漏但顺序不重要的场景。

**核心结构**

> 触发节点 → Checklist → 未通过则修正 → 全部通过则结束

**重点**

- 每一项都可快速判断通过或不通过。
- 只保留真正影响质量或风险的检查项。
- 对阻断项和普通提醒做区分。

**常见风险**

- 清单过长，实际不会执行。
- 使用“质量好”等无法判断的表述。
- 检查失败后没有补救动作。

## 5. 路由 / 自动化型

**适合**

信息录入、请求分发、AI 调用和输入输出相对明确的流程。

**核心结构**

> 接收输入 → 验证 → 判断 → 路由 → 执行 → 回执 / 记录异常

**重点**

- 定义输入要求和拒绝条件。
- 让路由规则互斥且可解释。
- 明确失败、重试、回退和人工接管。
- 区分“流程说明”与“已经实现的自动化”。

**常见风险**

- 把建议中的工具写成现有能力。
- 输入不完整仍继续执行。
- 没有幂等、重复或异常处理。

## 组合原则

- 顺序主干中出现少量异常：以顺序型为主，在相关步骤嵌入分支。
- 总调度流程包含验收：在流转节点嵌入短 Checklist。
- 路由后调用多个 SOP：以路由型判断，以总调度型展示下游关系。
- 一个流程需要同时使用三种以上模式时，优先拆成主 SOP 与下游 SOP。
