# New Element Backstage Check

Use this inside service-blueprint work when a new element may change the product's backstage logic while the user's frontstage path still looks familiar.

## Core Distinction

```text
前台体验相似，不代表产品本质相同；后台资源结构变了，体验物种也可能变了。
```

This is not a build/no-build opportunity judgment. Use `$product-opportunity-coach` for that. Here, focus on what the service blueprint must support.

## Backstage Checks

| Check | Question |
| --- | --- |
| 新资源 | What new resource powers the experience: AI context, user records, IP, community, capital, commerce, partner network? |
| 新角色 | Does the user become more than a buyer: contributor, data source, member, co-builder, investor, distributor? |
| 新流程 | What backstage process must happen that did not exist in the old product? |
| 新反馈 | Does the service create a recurring feedback loop instead of a one-time delivery? |
| 新收入 | Does the experience point to new monetization: subscription, service, commerce, licensing, community, revenue share? |
| 新增长 | Does the experience create a new growth loop: referral, content loop, member loop, data loop, IP loop? |
| 新风险 | What trust, privacy, delivery, or operational risk appears because of the new element? |

## Data And AI Example

If AI only writes or summarizes, it may be a frontstage efficiency improvement. If user records become persistent context and the product creates a continuous feedback loop, the backstage structure has changed. Check data capture, context maintenance, privacy, review cadence, human oversight, and action follow-up. Apply this only when the product actually uses those mechanisms.
