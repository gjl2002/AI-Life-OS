# Sales Architecture

Use this as a persuasion sequence, not a rigid visual template.

## 1. Hero: large future result

Answer immediately:

- What is the product?
- What result will the buyer obtain?
- In what period or through what mechanism?
- What name or short phrase should the buyer remember and repeat?

Pattern:

`Product name → identity/system result → period + final deliverable`

If the product name is hard to say, emotionally cold, or too internal, use a clearer public category phrase beside it. The hero should make the name feel like a verbal summon, not a database label.

## 2. Cognitive conflict

Break the buyer's old explanation without attacking the buyer.

Pattern:

`Most people think X causes the problem. The real constraint is Y.`

## 3. Failed path

Name recognizable attempts and explain why effort did not compound.

Pattern:

`Without A, the tool remains low-value state B.`

Use specific failures rather than generic pain language.

## 4. Unique mechanism

Introduce the product's causal model as a short sequence or flywheel.

Pattern:

`Step 1 → Step 2 → Step 3 → Step 4 → recurring result`

Explain why this mechanism succeeds where the old approach fails.

If a new element such as AI, automation, community, IP, commerce, or data changes the product logic, show the changed loop rather than writing "old product + new feature". Use `new-species-expression.md` when the page must explain a new category or new species.

## 5. Authority and proof

Answer “Why you?” with confirmed evidence:

- long-term practice
- real artifacts
- case studies
- customer feedback
- previous products
- measurable, sourced results

If proof is missing, use transparent founder-story context or mark `[待确认]`. Never manufacture impressive numbers.

Select proof that supports the same word-of-mouth sentence. Scattered praise is weaker than repeated evidence that makes users say the same thing.

## 6. Audience self-selection

Write each item as desire plus obstacle:

`Wants X, but is blocked by Y.`

Include exclusion criteria when useful.

## 7. Outcomes

Describe what the buyer will complete, own, or repeatedly be able to do.

Prefer:

- first completed artifact
- working behavior loop
- reusable system
- observable decision or workflow improvement

Avoid guaranteed life transformation.

## 8. System blueprint

Turn the abstract offer into a visible owned system.

Show:

- core identity or operating center
- modules and their jobs
- information or action flow
- feedback loop
- final integrated result

For new-species offers, the blueprint must show what changed backstage: context, data, role, resource, feedback, revenue, or growth loop. Otherwise the buyer will read it as a normal product with a nicer feature.

## 9. Curriculum or implementation path

Place this after the need and solution are understood.

Name stages by results, not lecture topics:

- weak: “tool introduction”
- strong: “establish personal context”

For each stage include:

- problem solved
- work performed
- deliverable completed

## 10. Bundle and rights

List everything the buyer actually receives:

- core course
- templates or system
- prompts, agents, or toolkit
- live sessions, support, or community
- updates and bonuses

Distinguish confirmed inclusions from planned items.

## 11. Price and action

State:

- price and valid currency
- truthful value comparison
- real deadline or capacity, if any
- refund/usage terms
- exact next step

Do not fabricate urgency. If commercial terms are missing, show `[待确认]`.

## Recommended page rhythm

Group the modules into four acts:

1. `Attention`: hero and cognitive conflict
2. `Understanding`: failed path and mechanism
3. `Desire + trust`: proof, audience, outcomes, blueprint
4. `Decision`: path, bundle, price, CTA

The two supplied reference PDFs validate this order: both delay curriculum and pricing until after the buyer understands the problem, mechanism, suitability, and outcome.
