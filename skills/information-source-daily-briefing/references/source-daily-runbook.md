## 1. 运行定位

信息源日报只回答：

> 我主动关注的这些来源，在当前时间窗口内出现了什么值得理解的内容？

它不回答“整个行业今天发生了什么”。当用户要求公共趋势、全网热点、竞品扫描或研究补充时，说明这属于另一个研究任务，不要把外部来源静默混入本日报。

默认窗口为滚动过去 24 小时。用户指定自然日、日期区间或其他窗口时遵从用户要求，并使用用户或运行环境的时区。

## 2. 首次连接

使用 Runtime 定位当前用户的「信息源」和共享「日报」。首次写入由用户确认结果，遇到同名时请其提供准确链接。预览仅需定位「信息源」。

如果用户只给出名称且工作区存在重名数据库，先请求准确链接，不进行大范围猜测。不要把某个公开模板的固定 ID 当作用户数据库。

根据模式获取：

- `信息源`：必需。
- 共享「日报」用于存放正式日报。由用户确认数据源，重新绑定模板后重新核验。
- `概念库`：只有用户主动启用概念沉淀时需要。

连接完成后仍应在每次写入前读取实时 schema，因为用户可能修改字段。

## 3. 数据库语义要求

### 信息源数据库

必须能够识别：

| 语义 | 常见字段名 | 要求 |
| --- | --- | --- |
| 来源名称 | 名称、Name、Title、来源名称 | 必需 |
| 关注状态 | 关注状态、Status、Following、启用 | 必需 |
| 来源网址 | 首选网址、网址、URL、Feed、RSS、Website | 至少一个 |

可以按需使用：

- 备用网址或次选网址；
- 来源平台或类型；
- 语言；
- 标签；
- 内容风格；
- 更新频率；
- 简介。

先读 schema 再映射语义。若同一语义对应多个字段且无法确定，向用户确认。不要自动创建字段、状态值或关系记录。

### 共享「日报」数据源

实时核验可写的标题属性、「标签」单选字段及精确选项「日报」。标题使用 `YYYY-MM-DD 信息源日报`，日期取报告在用户时区的归属日期。有独立的可写业务日期字段时可填写。系统创建时间用于记录页面创建时间。

库中可写的「核心判断」「行动建议」等属性按实际语义填写，完整报告保存于正文。

### 概念库

只要求能够保存：

- 概念名称；
- 简明解释；
- 来源名称；
- 来源链接；
- 与用户的关系或相关内容。

字段命名可以不同，以实时 schema 的语义为准。

## 4. 来源边界

日报候选池严格等于：

```text
云端信息源数据库
∩ 关注状态为启用
∩ 当前时间窗口内有已验证更新
```

不得自动加入：

- 官方 AI 公司新闻；
- 公共新闻网站；
- 热门榜单；
- GitHub Trending；
- 论文聚合站；
- Skill 作者的个人关注源；
- 模型凭常识推荐的来源。

如果上述来源本来就在用户关注列表中，则按普通关注源处理。

允许打开关注内容中的原始公告、论文、产品页面或引用链接进行事实核实。核实链接不自动成为独立日报条目，也不改变来源边界。

## 5. 时间与核验

### 核验优先级

1. RSS 或 Atom feed；
2. 来源官方提供的订阅地址；
3. 原始内容页面；
4. 频道页、作者页或公开接口；
5. 当前可验证的描述、摘要或文字稿。

### 覆盖状态

每个关注源只能标记为：

- `有已验证更新`：获得标题、链接和可信发布时间，且位于时间窗口内。
- `已验证暂无更新`：当前成功读取，并确认时间窗口内没有新内容。
- `未能验证`：当前读取失败、发布时间不清、反爬、网络错误，或只能获得旧缓存。

旧缓存只能帮助理解历史，不得证明实时无更新。

### 读取失败与回退

- 记录每个来源本次检查的入口和结果。对超时、429 或 5xx 等短时失败，可适当退避后重试，单个入口最多重试两次。需要更长等待时记入覆盖缺口。
- 可以使用用户登记的同一来源备用地址，或该来源的官方订阅或频道页。权限拒绝时报告限制。旧缓存、空响应和无法确认覆盖窗口的列表均不能证明没有新增。
- 视频源可先用 feed 确认窗口内更新，再补读原视频简介、章节及可访问的字幕或文字稿。只有标题时仅陈述更新事实。简介或章节用于说明涉及范围。视频论点应能追溯到具体字幕、文字稿或可核查的正文。视频正文无法读取时保留发现结果和证据限制。

### 整理候选

- 用用户时区确定时间窗口。时间记录带时区，按包含起点、排除终点核验窗口。
- 记录标题、原始链接和发布时间。正文、简介、章节或标题分别标注证据等级。
- 同一内容按原始链接或稳定内容 ID 去重。多个关注源谈同一事件时，可合并叙述并保留所有入选的证据链接。
- 筛掉广告、重复与明显离题内容，保留来源覆盖和筛选理由。新增很少时可交付短报。

## 6. 报告结构

### 今日核心判断

用一至数段说明：

- 今天新增是丰富、有限还是没有；
- 多个来源共同出现的主要信号；
- 对用户本次关注重点的意义；
- 来源覆盖是否完整；
- 今天最值得做的一件小事。

### 信息源读取覆盖

为每个关注源保留一条 Markdown 列表项，格式为 `- 来源名｜覆盖状态｜核验结果或失败原因`。覆盖状态使用「有已验证更新」「已验证暂无更新」「未能验证」。重名来源可加平台后缀来区分。报告的「今日核心判断」同时说明覆盖缺口。


### 今日新增

每条至少包含：

- 来源；
- 标题；
- 链接；
- 发布时间；
- 发生了什么；
- 为什么值得注意，以及判断依据是正文、字幕、简介、章节还是仅标题。

### 值得深看

只放值得用户投入完整阅读或观看时间的内容。内容不足时省略，不要求固定数量。

### 可以学习

提取可复用的概念、方法、表达方式或工作流。

### 可以收藏

保留未来可能用于创作、决策、系统设计或实践的素材。

### 对我的启发

结合用户在本次请求中主动给出的关注重点组织启发。没有个性化上下文时，只基于来源内容说明可能用途，不推断用户的商业定位、人生目标或身份。

### 今日行动建议

给零至三条当天可以完成的小行动。没有可靠行动时可以不写，不把阅读清单包装成行动。

### 概念库更新

仅在概念库已启用时出现。说明创建、更新或没有合格概念的原因。

## 7. 写回规则

### 写前质量检查

生成前保留从 Notion 实时查询得到的完整关注源名单。校验文件 `check.json` 记录带时区的时间窗口、关注源名称、每个来源的覆盖结果，以及入选报告的链接。

```json
{
  "window_start": "2026-11-24T08:00:00+08:00",
  "window_end": "2026-11-25T08:00:00+08:00",
  "followed_sources": ["示例频道"],
  "coverage": [
    {
      "source": "示例频道",
      "status": "有已验证更新",
      "detail": "官方订阅源验证了发布时间",
      "updates": [{"title": "示例视频", "url": "https://example.com/video", "published_at": "2026-11-24T12:00:00+08:00"}]
    }
  ],
  "report_urls": ["https://example.com/video"]
}
```

全部关注源都要有覆盖结果。「已验证暂无更新」和「未能验证」的 `updates` 为 `[]`，后者写明失败原因。`report_urls` 只列成稿引用的候选原始链接。链接可在可选板块重复引用。全部候选都被筛除时，在「今日新增」说明原因。核心栏目分别为「今日核心判断」「信息源读取覆盖」「今日新增」。

```bash
python3 scripts/report_quality_check.py --plan check.json --markdown draft.md
```

通过质量检查后再写回。脚本检查覆盖完整性、候选时间和链接，内容判断仍应对照原始证据。

### 写回共享「日报」

1. 核对目标的实时 Schema，并使用报告归属日期构造完整标题 `YYYY-MM-DD 信息源日报` 和 `标签 = 日报`。
2. 在同一数据源按完整标题和标签精确查重。唯一命中时局部更新本次报告内容。多个命中时停下来请用户确认。仅有同标题、其他标签的旧页时，说明冲突并请用户确认如何处理；当前请求授权前保留旧页。没有冲突且无匹配时创建。
3. 将实际字段和 `标签=日报` 传入 Runtime 的 `check-write`。只有通过预检并具备用户授权的写入权限时执行相应动作。标签选项缺失时，保留草稿并说明缺少的选项。
4. 回读确认归属数据源、实际标题、标签和完整正文。对获取到的完整 Markdown 重新运行质量检查。回读不完整时尝试按段取得正文，仍不足则标记回读未验证。
5. 修复确实缺失的链接时只更新对应段落并再次回读。创建状态不明时先查询已收到的页面 ID 或原查重条件，再考虑重试。


## 8. 概念库规则

概念库不是日报的必需依赖。

只有满足全部条件时才建议写入：

- 能在多个场景中复用；
- 有可靠来源链接；
- 能帮助未来理解、表达或实践；
- 不是一次性专有名词；
- 与现有概念相比有明确新增。

写入前搜索同名、别名和近似概念。优先更新原页面，并保留来源和本次新增理解。

## 9. 失败处理

| 情况 | 是否继续生成 | 是否允许写回 | 处理 |
| --- | --- | --- | --- |
| Notion 无法访问 | 否 | 否 | 说明连接失败 |
| 关注源数据库无法读取 | 否 | 否 | 请求正确链接或权限 |
| 关注列表为空 | 是 | 视用户要求 | 生成配置提示，不制造内容 |
| 所有来源当前无法验证 | 否 | 否 | 列出失败原因 |
| 部分来源无法验证 | 是 | 是 | 明确披露覆盖缺口 |
| 已验证但没有新增 | 是 | 是 | 生成简短无新增日报 |
| 日报数据源未确认、实时 Schema 不可核验或缺少标签「日报」 | 可形成草稿 | 否 | 说明对应缺口，保留草稿 |
| 概念库不可用 | 是 | 日报可写 | 跳过概念写入并说明 |

## 10. 自动化检查表

按顺序执行：

1. 读取自动化中已经确认的数据库链接和时间窗口；
2. 连接云端 Notion 并读取信息源实时 schema；
3. 查询启用的关注源；
4. 验证每个来源的当前覆盖状态；
5. 检查是否存在阻塞条件；
6. 只从已关注且已验证更新的来源建立候选池；
7. 去重、读取并核验内容；
8. 生成日报草稿；
9. 执行质量检查并核对候选证据；
10. 核验实时标签选项与数据源，按完整标题加标签查重；
11. 创建或更新日报；
12. 条件式更新概念库；
13. 回读日报和概念页面；
14. 报告写入状态、覆盖缺口和失败原因。

## 11. 最终自检

- 是否所有日报条目都来自用户关注源？
- 是否误把核实链接变成新的候选来源？
- 是否为每条信息保留了可点击来源？
- 是否正确处理时间窗口和时区？
- 是否把未能验证误写成无新增？
- 是否为了凑数量加入低价值内容？
- 是否使用了用户未提供的商业定位或个人假设？
- 普通调用是否已经写入并完成回读？
- 用户明确要求仅预览时，是否没有写入 Notion？
- 是否按实际数据源、完整标题与「日报」标签查重并回读？
- 概念库是否真的被用户启用且达到准入条件？
