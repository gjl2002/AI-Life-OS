## 用户自己的 Notion 接入

本 Skill 使用 `$ai-life-system-init` 定位用户自己的 Notion 结构。执行前先运行 `scripts/runtime.py status`；状态为 `needs_init` 时先引导用户完成初始化。对本次操作涉及的每个概念运行 `scripts/runtime.py resolve --concept <key>`，只使用 Runtime 返回的目标 Data Source ID。读取该 Data Source 的实时 Schema，并在写入前运行 `scripts/runtime.py check-write` 校验本次属性、选项和 relation。

概念映射：`item, wardrobe, digital_device, gift, relationship_circle`。

创建时必须让当前 Notion connector 将新页面的 parent 指向已解析的 Data Source；写入后回读确认 parent 和属性。若概念未找到、结构不兼容、候选不唯一或 connector 无法确认 parent，应停止该写入并说明原因，不得猜 ID、扫描无关空间或复制已有个人记录。以下正文中的数据库路径、字段名、选项和默认值若与用户实时 Schema 不一致，均视为示例而非要求；只有语义和字段类型明确匹配时才映射，否则询问或安全停止。仅读取本次任务所需的数据；不得将用户本地索引、凭据、页面 ID 或个人样例打包发布。

# Item Tracker — Notion 通用物品录入（含送礼联动）

覆盖三个物品库：**衣橱（衣服）/ 产品（数码）/ 物品**，并按需联动 **礼物 / 人际圈**。一个技能通吃，按用户说的词自动判库。

## 数据库（自动判库）

|---|---|---|---|

判库原则：明确说衣橱/衣服→衣橱；数码/产品/电子→产品；物品或未指明→物品。**提到"送/收到礼物"→ 走送礼模式**（见下）。判不准就问。

## 三库通用字段（走同一套流程）

名称、图片、状态、获取方式、获取日期、相关人物、礼物
差异字段见 [references/database-schema.md](references/database-schema.md)。

## 输入解析

| 字段 | 来源 |
|---|---|
| 名称 | 链接/照片识别(需确认)/用户描述 |
| 品牌·品类·类别·颜色·尺寸(衣橱) / 品牌·品类(产品) / 分类·特性(物品) | 链接提取 / 照片识别(需确认) / 用户描述 |
| 入手价 | 自购时**必须用户确认实际支付价**；赠送一般无价，留空 |
| 获取方式 | 用户明确提供时填写；无法判断时询问或留空，不猜购买方式 |
| 获取日期 | 具体日期；相对日期用当前日期推算 YYYY-MM-DD |

缺关键信息（获取方式、获取日期等）时一次性问清，不猜。

## 信息获取三通道（交互自由）

1. **有购物链接** → 抓链接取信息（名称/品牌/品类/参考价），最准。
2. **只有照片** → 先以图搜图（visual_search + 京东/淘宝/闲鱼搜图）找同款候选 → **必须把候选发给用户确认（"是不是这件"）** → 确认后补全；识别不到 → 只上传照片＋问用户名称/品牌。
3. **无链接无图（纯描述）** → 按描述建，缺的问用户。

**图片原则**：用户发的是随手拍/实物照时，优先用 `visual_search`/`image_search` 找到**官方产品图**（电商/官网图）上传，更专业；找不到才用实物照。

## 最稳定执行流程（务必照此，勿走捷径）

> 目标：生成目标库可见、属性齐全、不产生垃圾页的正常记录。

### 0. 判库 + 收集
- 判目标库；判断是否送礼模式。
- 从链接/照片(经确认)/描述收集字段；缺失关键信息就问。

### 1. 直接新建记录
- 通过当前 Notion connector 在 Runtime 解析出的目标 Data Source 下新建记录，拿到返回的 page_id，并核对 parent。

### 2. 上传图片
- `notion-create-attachment`：`source_url` = 官方产品图直链（或实物照直链）。
- ⚠️ 附件 `aka.doubaocdn.com` 等链接会重定向，需先 `curl -L -s -o /dev/null -w "%{url_effective}" "<url>"` 追踪出最终直链再传。
- 拿 `file_upload_id`。无图则跳过，交付说明"图片待补"。

### 3. 检查 select 选项
- 以实时 Schema 返回的当前选项为准，只用已有且语义匹配的值。
- 若所需值不存在，不自动改用户的 Schema；询问用户是否要调整结构，或留空并说明。

### 4. 一次性 update 属性
- `notion-update-page`（`update_properties`），page_id = 新记录。
- 填：通用字段 + 该库差异字段（见 references），日期用 `date:获取日期:start` + `date:获取日期:is_datetime:0`。
- 图片格式：`"图片":[{"type":"file_upload","file_upload":{"id":"<file_upload_id>"}}]`。
新页面只写本次记录明确提供的值；未提供的可选字段留空，不沿用其他记录的属性或正文。
  - 产品库 `入手价`（赠送/未知价时置 null，否则填用户确认价；勿保留既有页面的价，例如某商品的示例价格）；
  - relation 字段 `相关人物`/`礼物`/`衣服`/`物品`/`产品` 里既有页面带进来的旧指向（送礼模式会被覆盖为新关联，否则置 null）；
  - 各库专属值字段（衣橱 `尺寸`/`颜色`/`季节`/`场景`、产品 `转卖价格`/`退休日期`、物品 `处理日期`）若非新记录内容也要清。
- 状态仅在用户实时 Schema 有语义匹配选项且上下文明确时填写；否则留空或询问。

### 5. 验证
- `notion-fetch` 新记录，确认 `parent-data-source` = 对应库、属性落库、图片挂载。
- 向用户报告，主观字段留空。

## 送礼模式（"XX 送了我 XX" / "收到的礼物"）

触发：用户说谁送了我/收到了/谁给我的某个东西。此时在录入具体物品外，还要**建礼物记录 + 关联送礼人**，形成 人⇄礼物⇄物品 三方闭环。

### A. 定位或新建送礼人（人际圈）
- **找到** → 用现有 person page_id（使用 Runtime/当前用户数据库搜索返回的页面标识）。
新页面只写本次记录明确提供的值；未提供的可选字段留空，不沿用其他记录的属性或正文。
- 与用户确认这个人是不是正确的（重名人时）。

### B. 录入具体物品
- 照「最稳定执行流程」把物品录进对应库（衣橱/产品/物品），拿 item page_id。
- 获取方式 = 赠送；入手价留空（或用户给）。

### C. 建礼物记录（礼物库）
新页面只写本次记录明确提供的值；未提供的可选字段留空，不沿用其他记录的属性或正文。
- update 属性：`礼物`(title)=物品名、`送给/收到`=收到、`日期`=`date:日期:start`、`性质`(multi_select)=按场景（生日/节日/日常/周年纪念日礼物，猜不准就问）。
新页面只写本次记录明确提供的值；未提供的可选字段留空，不沿用其他记录的属性或正文。

### D. 三方关联（一次写全）
- 礼物页：`朋友`=["<person_url>"]、对应物品字段=`["<item_url>"]`（衣橱→`衣服`、产品→`产品`、物品→`物品`）。
- 人际圈人页：`礼物`=["<gift_url>"]、对应物品字段=`["<item_url>"]`。
- 物品页：`相关人物`=["<person_url>"]。
- relation 属性值 = 目标页 URL 数组。

### E. 验证
- fetch 礼物页、人页、物品页，确认三方关联都写进去。
新页面只写本次记录明确提供的值；未提供的可选字段留空，不沿用其他记录的属性或正文。

## 不碰

- 主观字段：衣橱 `喜爱程度`/`常穿程度`；产品 `使用频率`/`满意度`；物品 `情绪价值`/`特性`/`描述·故事`。
- 公式字段：衣橱 `使用标签/信息汇总/基础标签/总日均/星级评分`；产品 `使用状态/总日均/核心评估`；物品 `概览`；礼物 `分类`。
- 按钮：`同步至礼物`、`同步至产品/物品/衣服`、`已退休`、`已处理`。
- 礼物库的 `产品/物品/衣服` 三字段：送礼模式中只填实际对应的那一个。

## 边界

- 搜不到同款 / 无链接 → **先建一条**（名称=照片识别结果或"待命名"），只传图，其余留空，告知用户后补。
- 模板页绝不能当既有页面。
- 自购价/尺寸/颜色等实际值须用户确认，不猜。
- 送礼人信息不全（关系/性别等）→ 仅当用户明确要求且目标数据源可写时，才创建最小人脉记录；否则询问或暂不关联。
